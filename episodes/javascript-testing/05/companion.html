Parisa I ran the test suite and received twelve order receipts.

Jules Please tell me they were sent to a test inbox.

Parisa In this fictional incident, yes. In my actual emotional state, I have concerns.

Jules Today we replace a dependency so we can test the code without sending real messages.

Parisa This sounds like the part where we lie to the software.

Jules In a controlled and clearly labelled way.

Parisa Welcome to Okay, But Why?. Professional lying, with cleanup afterward.

Why Replace Anything?

Jules Our fictional order code decides whether to request a receipt. The real delivery dependency might contact an email service. We don't want every focused test to require that service or send a message.

Parisa Cost, speed, reliability, privacy, and side effects. Also I need to test an email failure on demand, not wait for the provider to have a difficult afternoon.

Jules Exactly. A test double stands in for a dependency. We control its behavior so the test can ask a specific question about the code around it.

Parisa Like a rehearsal partner who reliably says the cue line. Useful when I'm testing my response, less useful when I'm trying to learn how actual customers behave.

Jules Good limitation. The double only behaves as we've programmed it. It cannot prove the real dependency matches our assumptions.

Parisa So every replacement trades realism for control. We should know where the trade occurs.

Jules Yes. The goal isn't maximum mocking. It's enough control to isolate the question, while retaining the real behavior we want evidence about.

The Vocabulary Is Less Stable Than the Concept

Parisa Mock, stub, spy, fake. Are these different objects or four words developers use to start arguments?

Jules Both, depending on the conversation. A stub usually supplies predetermined answers. A spy records interactions such as calls and arguments. A fake is often a simplified working implementation, such as an in-memory repository.

Parisa And mock?

Jules Sometimes a general name for any double; sometimes specifically an object with expectations about interactions. Libraries use these terms differently. Describe what the replacement does instead of assuming the label settles it.

Parisa “This function returns an accepted receipt result and records its arguments” is clear even if we disagree about its taxonomic family.

Jules Exactly. Vitest's vi.fn can be configured with behavior and can record calls. That means one object may serve both stub-like and spy-like roles.

Parisa The important questions: what is real, what is replaced, what answer does it give, and what observation are we making?

Jules Those four questions prevent most mock confusion before the vocabulary debate starts.

Pass the Dependency Like Ordinary Data

Jules Let's use a small function whose job is to request a receipt for an accepted order. It receives the sending function as an argument.

Parisa This function is synchronous. Returning true means it invoked the supplied function, not that a real email arrived.

Jules Exactly. We're defining that narrow contract explicitly. A production delivery workflow would need asynchronous results, errors, retries, and other decisions. We tackle promise outcomes in Episode Eight.

Parisa Passing sendReceipt is dependency injection in ordinary JavaScript. Functions are values; we can pass one to another function. No special testing syntax required.

Jules In the real application, the caller supplies the real dependency. In this focused test, we supply a controlled function.

Parisa And order.email is synthetic data in our test. We don't fetch a real customer's address to make the example feel authentic.

Jules The replacement doesn't send anything. Vitest records that our real function called it once with the expected payload.

Parisa Vi is the Vitest utility object. Fn and those call matchers are testing APIs. The object literal, import, and ordinary function call are JavaScript.

Jules Right. This is an interaction test because requesting the dependency is the behavior under examination.

Is That an Implementation Detail?

Parisa Earlier we said don't obsess over whether a helper got called. Now we're counting calls. Have we contradicted ourselves before lunch?

Jules The distinction is why the interaction matters. Here the operation's contract is to request a receipt once for an accepted order. The dependency call is the observable boundary of that responsibility.

Parisa If we were testing an internal helper named buildReceiptPayload, requiring it to be called once might just freeze the current structure.

Jules Exactly. A useful interaction assertion protects a meaningful effect: don't send when rejected, send the intended data, avoid duplicate requests within the operation.

Parisa But even our one-call assertion doesn't prove exactly-once email delivery across retries, crashes, or repeated HTTP requests.

Jules Correct. It proves one invocation in this local scenario. Distributed delivery guarantees require more design and different tests.

Parisa That distinction matters. “Called once” in a unit test is not the same promise as “the customer can never receive two receipts.”

Jules Yes. Give the test its actual scope, and it remains useful without making impossible claims.

The Negative Case Is Often the Point

Jules What other case should we write?

Parisa A rejected order must not request a receipt. That's a meaningful absence of a side effect.

Parisa If the function returns false but still sends the message, the second assertion catches it. Return value alone wasn't enough.

Jules Exactly. And we create a fresh mock function in each test so prior call history can't contaminate the result.

Parisa A negative assertion also needs the correct observation window. In this synchronous function, after it returns is enough. If it schedules work later, checking immediately may be premature.

Jules Excellent async preview. “Wasn't called yet” isn't always “will not be called.” Control or await the relevant lifecycle.

Parisa We should be as careful with absence as with presence. Silence at one instant is a small observation.

A Stub Supplies a Situation

Jules Suppose another function asks a stock service how many pizzas are available. A stub can return zero so we can reliably test the sold-out path.

Parisa I don't need to empty the actual restaurant. The dependency's answer creates the condition.

Jules Right. Then we call the real ordering logic and assert the sold-out response. We're testing how our code responds to that answer, not whether the stock service correctly counts pizzas.

Parisa What makes a bad stub?

Jules One that supplies impossible or incorrectly shaped data without acknowledging it. If the real service returns an object with availableCount and the stub returns a bare number, we might test a fantasy interface.

Parisa Or if every stub immediately succeeds, we build a suite set in a universe without failures, delays, or malformed responses.

Jules Exactly. Use representative success and failure shapes informed by the actual contract. Validate external data where appropriate and test that validation separately.

Parisa A TypeScript interface helps describe expected shape during development. It doesn't guarantee the external response obeys it, or that our mock has captured all its semantics.

Jules So keep the real integration represented in other tests, and update doubles when the contract changes.

Spies Can Still Do the Real Thing

Parisa What about spying on an existing object's method?

Jules A spy can observe calls to an existing function. In Vitest, spying on a method doesn't automatically mean the original implementation stops running. You must deliberately replace its behavior if the real side effect should be prevented.

Parisa Critical. “I put a spy on sendEmail” is not a guarantee that no email was sent.

Jules Exactly. For our teaching example, injecting a fresh vi.fn is clearer because there is no original side effect to accidentally preserve.

Parisa If I do spy on an existing method, I need to understand whether it calls through, how to replace its implementation, and how to restore it afterward.

Jules Yes. The tool name alone doesn't settle those semantics. This is a good moment for “Jules Googles It,” except we use the installed version's documentation instead of folklore.

Parisa Excellent. Professionals look up the exact behavior before pointing a test at an email sender.

Clearing, Resetting, Restoring

Jules Three cleanup words that sound interchangeable and aren't. Clearing usually removes recorded call history. Resetting also changes mock behavior according to the tool's reset semantics. Restoring puts an original spied-on implementation back.

Parisa And exact details vary across tools and versions, so don't memorize a vague cross-framework slogan as an API contract.

Jules Right. For Vitest spies, mockRestore is the targeted operation when we want the original method back. Global cleanup helpers and configuration options exist, but their scope matters.

Parisa Restoring spies doesn't mean every fake timer, global stub, or module cache modification has been undone. Each kind of replacement can have its own lifecycle.

Jules Exactly. Use cleanup appropriate to what you changed. Fresh local doubles are often simpler than modifying globals.

Parisa And cleanup belongs in a runner-managed teardown or a try-finally when necessary, so a failed assertion doesn't skip it.

Jules Yes. A leaked mock can make the next test pass or fail for the wrong reason, especially when tests share a process or state.

Parisa The replacement has to leave the rehearsal room when its scene ends.

Module Mocks Have Extra Machinery

Jules Sometimes a dependency is imported directly into the module rather than passed as an argument. Runners provide module mocking to replace what that import resolves to.

Parisa Useful, but now we're interacting with module loading and transformation, not just passing a function.

Jules Exactly. Hoisting, import timing, caches, and ESM restrictions can affect behavior. Vitest and Jest don't have identical rules in every mode.

Parisa So this series isn't going to pretend vi.mock is a magical ordinary function call that can be placed anywhere and behave the same way.

Jules Correct. Use it when appropriate, consult the relevant docs, and keep the replacement close to the external boundary. Don't mock the module you're supposedly testing and then assert its configured answer.

Parisa That's the classic “I told the mock to return pizza, and astonishingly, pizza.” The application has contributed nothing.

Jules A real function under test must still run. Otherwise we're only checking that our test double remembers its instructions.

Parisa And don't rewrite an entire application around injection just to avoid learning module mocks. Choose a sensible seam for the actual project.

Fakes Need Their Own Skepticism

Jules An in-memory repository can be a useful fake for fast tests. It stores and retrieves records without a real database.

Parisa But JavaScript object lookup doesn't reproduce database uniqueness constraints, transactions, collation, query behavior, or concurrency.

Jules Right. A fake can answer a narrower question about application decisions. Real-database integration tests cover the persistence behavior it cannot reproduce.

Parisa And maintaining a sophisticated fake can become a second implementation of the database. Then we have two systems and one is mostly wishful thinking.

Jules Keep it small, and know its limitations. If the test's question is about a database constraint, use the actual database technology in an isolated test environment when practical.

Parisa Same with a fake authentication layer. Convenient for rendering a signed-in UI. Not evidence that the server enforces authorization correctly.

Jules Exactly. UI state and security enforcement are separate responsibilities.

When Mocks Make Refactoring Hurt

Parisa A test checks that function A calls B, B calls C, and C calls D. I combine B and C. Behavior is unchanged. Everything fails.

Jules The tests encoded the internal call graph. Sometimes that graph includes meaningful contracts, but often it's incidental structure.

Parisa Repair by testing the public result or external effect where possible. Keep interaction checks only where the interaction itself matters.

Jules Yes. Also watch for tests that specify every argument in enormous detail when only a few fields are relevant to the contract.

Parisa Though don't make assertions so partial they miss unsafe extra data. A receipt payload that accidentally includes a secret deserves a failure.

Jules Good correction. Partial matching is a choice, not automatically better. If the allowed payload shape is security-relevant, assert the full intended shape or validate it explicitly.

Parisa Again, why are we checking this? “Less brittle” shouldn't mean “unable to notice meaningful differences.”

The Contract Has to Meet Reality Somewhere

Jules How do we stop a test suite full of doubles drifting away from reality?

Parisa Keep some tests at real integration boundaries. Use documented contracts, representative fixtures, and intentional updates. Where useful, contract tests can check that consumer expectations and provider behavior remain compatible.

Jules A contract test doesn't necessarily exercise the whole user journey, but it can detect mismatched request or response assumptions.

Parisa And a sandbox provider test still has limits. It may not reproduce all production behavior, regional rules, rate limits, or failure modes.

Jules Exactly. Evidence from different scopes complements itself. We don't need every focused test to hit a real service, but we shouldn't have no test ever connect the actual wires.

Parisa Nor should ordinary automated tests hit a production service just because that's the most “real.” Use isolated environments and test credentials with appropriate permissions.

Jules Controlled realism, chosen for the question.

Listener Workshop — Which Thing Is Real?

Jules A test replaces the payment client with a function that resolves to approved. It calls the real checkout service and checks that an order becomes accepted. What does it establish?

Parisa That the checkout service follows its acceptance path for the approved response we supplied, under this setup. It doesn't prove the provider approves real payments or that our HTTP adapter sends a valid request.

Jules What other scenario would you want?

Parisa Declined payment. A dependency error. Maybe an uncertain outcome or duplicate request, depending on the contract. Those might need distinct behavior, not a single generic failure bucket.

Jules What would be an over-mock?

Parisa Replacing the checkout service itself with a function that returns accepted and then asserting accepted. We skipped the subject.

Jules What would be an unsafe setup?

Parisa A spy that still invokes a live payment method, or real credentials exposed to untrusted test code. Use the controlled dependency and isolated environment deliberately.

Rehearsal: A Dangerous Spy

Jules Let's repair the fictional receipt incident from the opening. Someone attaches a spy to the mail client's send method, calls requestReceipt through the real adapter, then checks that send was called once. Messages appear in the test inbox.

Parisa First, stop using that path until we understand the side effect. The spy observed the original method but didn't replace it. We wanted a controlled dependency, not a witness.

Jules The author says the assertion passed, so the test worked.

Parisa The assertion worked, but the test setup violated our intention to avoid real delivery. Passing doesn't excuse an unwanted side effect.

Jules How do we repair it?

Parisa For the focused receipt-decision test, pass a fresh local double directly. For an adapter test, replace the actual network boundary or use an isolated service designed for testing, with explicit configuration and restricted credentials.

Jules And verify that the test cannot quietly fall back to the production endpoint.

Parisa Exactly. Configuration should fail clearly if the isolated environment isn't present. A fallback to live service is the wrong kind of helpful.

Jules The double's return value should match what the caller expects, too. If the real method returns a promise and the replacement returns undefined, timing and error behavior may differ.

Parisa Right. Shape includes asynchronous behavior, not just object properties. A promise-returning contract needs a promise-like success or failure in the test when that behavior matters.

Jules Then cleanup restores any modified method, and a separate integration check covers the real adapter's request shape.

Parisa Now we can say which responsibility each check protects. We didn't merely turn the inbox off and hope the evidence remained valid.

Call Order Can Be Meaningful or Accidental

Jules What if a test asserts that validation happens before saving? Is that too internal?

Parisa It depends on the contract. If invalid input must never be persisted, the important observation is no save for invalid input. That can avoid coupling to the exact helper sequence.

Jules But some workflows really require an order, such as establishing authorization before performing a protected effect.

Parisa Then test the externally meaningful guarantee. We may need interaction evidence, but phrase it around the safety property rather than the current function names.

Jules So “doesn't write for an unauthorized request” is often stronger and clearer than “calls checkPermission before call number three.”

Parisa Yes. Though temporal ordering can matter when the side effect itself reveals data or consumes resources. Choose an observation that would fail for the actual unsafe behavior.

Jules What about counting log calls?

Parisa If the log is an audit requirement, maybe. If it's a debug message somebody happened to add, probably not. Logging can be a real product or operational contract, but it shouldn't become sacred accidentally.

Jules And don't assert that sensitive data appears in logs merely because the current implementation prints it.

Parisa Please no. Characterizing a leak isn't endorsing it. The desired test may be that the sensitive field is absent.

A Double That's Too Helpful

Jules Another subtle failure: our fake repository returns a record even when the requested ID is wrong. Every lookup succeeds.

Parisa Then a bug in the ID passed by the application may never surface. A realistic enough fake should distinguish the relevant IDs or the test should assert the request argument if that's part of the boundary.

Jules Exactly. A double that accepts anything can hide incorrect collaboration.

Parisa But making the fake reject every unspecified detail can make tests brittle. We need to encode the relevant contract, not every incidental option.

Jules That balance takes judgment. Ask what mistakes the double should help expose and which details the test intentionally ignores.

Parisa I like to imagine introducing a plausible bug. Wrong order ID, missing email, sending for rejected orders. Would this test fail? If not, either the test isn't aimed at that behavior or the assertion needs work.

Jules A small manual mutation check can make that concrete before adopting any mutation-testing tool.

Parisa And if every bug I imagine still passes, the mock may be starring in its own fictional production. Time to reconnect the subject.

Write Down the Replacement Boundary

Jules A short test comment can help when a double's limitation isn't obvious. Something like: real checkout decision, controlled payment response, adapter covered separately.

Parisa That's useful context, unlike a comment that says “create mock” above the line creating a mock. Explain the choice or limitation the code can't show by itself.

Jules And keep it accurate as the suite changes. If the separate adapter test disappears, that comment becomes a false reassurance.

Parisa Same with fixture responses copied from old documentation. They need review when the contract changes. The replacement is maintained code, not a frozen souvenir from the first implementation.

Jules A double should make the question easier to ask while keeping its assumptions visible.

Parisa Good. We can lie to the dependency without lying to ourselves about what we tested.

Okay, That's Why

Jules Test doubles make dependencies controllable so we can test our code's decisions and interactions without unnecessary real side effects.

Parisa They also create assumptions. Keep those assumptions visible, clean up replacements, and connect to reality with other tests.

Jules Next: the DOM. Buttons, labels, simulated browsers, and why querying by role can reveal a better interface.

Parisa Our software lies now come with accessible names.
