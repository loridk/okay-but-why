Companion reference

A Lighthouse accessibility score of 100 is not proof that a site is completely accessible. It summarizes scored automated checks, not every requirement, page state, interaction, or human experience. This developer pass is not a formal audit or conformance certificate.

Developer accessibility-testing checklist

  1. Define a real task and scope. Record page/route, user state, viewport, browser, relevant versions, and tool configuration. Use safe test data. Include initial, open, invalid, loading, success, and failure states where relevant.
  2. Run automated checks. Use Lighthouse and/or axe-based checks deliberately; account for overlap. Run scans after relevant state changes, not only on the initial page. Investigate failures and incomplete/manual-review results.
  3. Put away the mouse. Complete the essential journey with Tab, Shift+Tab, and the appropriate activation/widget keys. Check every action has a usable keyboard path; test results, not only event firing.
  4. Check focus. Is it visible and unobscured? Does the order make sense? Do dialogs have an entry, containment while modal, an exit, and a logical return? Do routine updates preserve the user's position?
  5. Enlarge and reflow. Check text resizing, narrow effective layout, wrapping, clipping, sticky content, dialogs, and error recovery. See Episode 5 for scoped reference values.
  6. Review visual meaning. Check contrast in actual states/themes, color-independent information, useful labels, target size/spacing, and reduced-motion behavior. Investigate backgrounds and states automation cannot evaluate reliably.
  7. Inspect the accessibility tree. Check computed role, name, state, description, and relevant ID relationships. Inspect before/after activation and correction; identify which naming source actually won.
  8. Use a screen reader. Learn basic commands for one supported combination, then follow the task. Navigate both document structure and controls. Check names, groups, instructions, errors, announcements, and final outcome. Record environment and modes.
  9. Think like a human. Is alternative text appropriate in context? Are names and headings useful? Are instructions, interaction effects, and recovery understandable? Developer testing complements experienced-user involvement.
  10. Report, fix, and verify. Record steps, expected/actual behavior, impact, and evidence. Add a meaningful regression check when it can protect the behavior. Recheck the failure and related states. Document untested scope.

What each tool contributes

Lighthouse
A convenient automated page snapshot and repeatable checks. The accessibility score excludes manual checks and does not measure complete WCAG conformance or journey success.
axe-core / axe DevTools
Axe-core is an automated rules engine that can run in browser testing and other tools. DevTools products provide testing interfaces. Scan rendered states; supplement with behavior and manual evaluation.
WAVE
Visual annotations for errors, alerts, and structural information. Interpret categories and context; an alert needs investigation, not automatic deletion.
Browser accessibility inspectors
Evidence of the browser's computed accessibility information. They help explain wrong names, missing roles, and stale state; they do not reproduce every screen-reader announcement.
Linters and framework warnings
Early source-level checks. Custom components may need configuration; runtime content, CSS, and interaction remain outside many static checks.
Interaction tests
Exercise known keyboard/focus/application outcomes and protect regressions. Test selection and assertions limit what a green result establishes.
Manual and experienced-user evaluation
Inspect context, task completion, reading/navigation, presentation changes, and usability that automated rules cannot settle.

Screen-reader starting workflow

  • Choose a supported browser/screen-reader combination; record versions and settings.
  • Learn start/stop, speech interruption, heading navigation, control navigation, and reading versus interaction modes from its own guide.
  • Practice on a familiar structured page before diagnosing your application.
  • Test reading structure as well as Tab navigation. A screen reader's reading cursor and DOM focus are not identical.
  • Check available name/role/state and useful outcomes rather than requiring identical wording across products.
  • Do not treat five minutes of developer use as a substitute for experienced-user testing.

Keep checks inside development

Design decisions → semantic HTML → accessible interaction → state-based automated checks → manual journey verification → regression protection and continued evaluation. A component can pass alone while its composition or content fails; check important journeys too.
