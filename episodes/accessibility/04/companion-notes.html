Practical ARIA decision guide

  1. Can native HTML express this correctly? Use it: button, link, checkbox, details/summary, dialog, label, fieldset/legend, and appropriate document structure.
  2. What semantic information is missing? Identify the specific role, name, description, state, or relationship. Add only attributes supported by that element/role.
  3. What behavior is still missing? Implement the relevant keyboard pattern, focus management, visibility, and activation behavior. ARIA does not implement these.
  4. Can the state change? Derive visible and exposed state from the same decision. Test every opening, closing, selection, validation, and failure path.
  5. What does the browser expose? Inspect the computed role/name/state and references, then test the actual interaction and relevant assistive-technology experience.
  6. Cannot explain the attribute's job? Look it up before adding it. Attribute count is not an accessibility measure.

Naming and descriptions: choose deliberately

Visible native label / button text
First choice where appropriate. Associate a label with its input; use meaningful button text. Visible labels help people beyond screen-reader users.
aria-labelledby
Uses text from referenced element IDs as a name. Useful for naming a dialog from its visible heading or combining necessary visible context. IDs must be unique and references valid.
aria-label
Supplies a name string directly when a supported element needs one and suitable visible text is unavailable, such as an icon-only close button. It does not create a visible label.
Naming precedence
For ordinary supported controls, valid aria-labelledby takes priority over aria-label, which can override native/text naming. Element-specific computation rules matter. Prefer one intentional strategy and inspect the computed name.
Visible words stay in the name
A visible “Remove” control can be named “Remove margherita pizza.” Avoid renaming visible “Pay now” as “Complete transaction.” Mismatches can obstruct voice control.
aria-describedby
References supplementary help or error text. It describes rather than replaces the name. Keep important information available visually too. Changing a description is not a guaranteed immediate announcement.

States and relationships quick reference

role
Identifies semantics such as dialog or status. Native HTML often supplies an implicit role. Assigning a role creates expectations; it does not supply the interaction.
aria-expanded
Reports whether controlled content is expanded. Put it on the appropriate controlling element and synchronize it with actual visibility.
aria-controls
References the controlled element's ID. It does not toggle, move focus, or guarantee an assistive-technology shortcut. It is optional in the APG disclosure pattern.
aria-selected
Selection state for supported roles such as tab or option. Distinguish focus from selection; implement the widget's keyboard pattern.
aria-checked
Checked state for supported custom checkable roles. Prefer native checkbox/radio controls and their native checked state. Mixed state belongs only where supported and meaningful.
aria-pressed
Pressed state for a toggle button. It is not a substitute for expanded, selected, or a checkbox's checked state.
aria-disabled
Communicates unavailability without disabling activation or changing tab order by itself. Enforce every activation path. Native disabled has its own behavior and form-submission consequences.
aria-current
Identifies the current item in a set, for example page for the current navigation link or step in a process. It does not navigate or select a widget option.
aria-invalid
Marks a detected invalid value. Update it with validation state and associate useful error text. Do not declare untouched fields invalid merely because they are initially empty.
aria-hidden
Excludes an element and its subtree from the accessibility tree. It does not visually hide or disable them. Never leave focusable controls within an aria-hidden subtree. A child set to false cannot undo a true ancestor.

Visibility is not one switch

  • hidden normally hides content visually and from accessibility exposure. It is an HTML boolean attribute: hidden="false" still means present. The JavaScript element.hidden property accepts a boolean.
  • aria-hidden="false" is an ARIA value, not the same boolean-attribute mechanism. It cannot override another reason content is hidden.
  • inert prevents interaction/focus and removes a subtree from accessibility exposure; it does not itself create visual styling.
  • Visually hidden text can intentionally remain available to assistive technology. Do not confuse that pattern with display: none.

Live updates without stealing focus

role="status"
Useful for nonurgent results such as “Item added to cart” or “Six delivery slots available”; implicitly polite, with atomic announcement semantics.
role="alert"
Assertive, atomic live semantics for urgent information. Avoid using it for routine updates or combining multiple announcement mechanisms unnecessarily.
aria-live="polite" / "assertive"
Specify update-announcement priority on an appropriate region. These are not guaranteed speech delivery or exact timing APIs.
  • Create the region before changing its content; test timing and browser/assistive-technology combinations.
  • Announce confirmed results, not merely attempted operations.
  • Keep messages concise, relevant, and available for later review when needed.
  • Do not announce a whole refreshed page or sensitive values such as the copied password.
  • Check repeated identical messages, rapid updates, and concurrent focus changes.
