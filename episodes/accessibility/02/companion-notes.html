The browser derives accessibility information from the document and exposes it through accessibility APIs. A matching screenshot does not imply matching semantics or behavior.

Choose from the job, then style it

Go to a destination
Use an a element with a real href. Preserve browser navigation conventions when using a client-side router.
Perform an action
Use button. Specify type="button" for non-submit actions inside forms; use type="submit" intentionally.
Identify content hierarchy
Use meaningful headings and levels. CSS controls size; heading semantics communicate structure.
Group items
Use lists when items form a list; do not rely on decorative bullets alone.
Identify major page areas
Use main and appropriate nav elements. Name multiple navigation landmarks distinctly when needed. Avoid region clutter.
Name an input
Use a persistent visible label. An explicit label's for matches the input's unique id; the input's name serves form submission.
Group related form choices
Use fieldset with a useful legend. Native radio buttons with the same name provide mutually exclusive selection.
Present tabular data
Use a table, meaningful header cells, and an appropriate caption. Do not use a data table merely for page layout.

Inspect the rendered result

  1. Inspect the actual HTML element, not the framework component's name.
  2. Inspect the computed accessibility role, name, and relevant state.
  3. Check heading and landmark structure for useful navigation.
  4. Operate the control and complete its task; semantics alone do not establish behavior.
